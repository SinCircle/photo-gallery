# 2026-10-06 转场与工具条细节修复

本轮基线是上一轮性能优化的最终构建（本地 5193 端口，冻结于 `.superpowers/verification/performance-sweep/after/dist`）；候选构建通过 5187 端口检查。未部署到 80 端口。原有三点推入加载动画和文字阴影算法均保留。

## 改动

- 移除整张放大照片的原生 View Transition 快照；转场复用浏览器已经解码的图片，以视口裁剪的独立合成层移动。保持 680ms 非线性曲线、双向几何衔接和滚动位置恢复。照片层 z-index 10，实际工具条与离场工具条层均为 20。
- 首页离场只保留当前可见卡片，返回时优先复用已有照片列表。图片、玻璃的重初始化仍等转场结束；首次画廊的日期颜色读取也推迟到转场完成后的空闲时间。日期格式器和亮度查找表复用。
- 展开文字取消 576ms 延迟，立即淡入，220ms 完全显示。元信息不再等待整个字体集合的 `fonts.ready`；字体尚未就绪时显示备用字体。
- 首次移入收起的圆点并立即点击，只展开工具条，避免误触正在出现的返回按钮。

试验中发现，复制原图到新的 2D 画布会在本机触发昂贵的像素转换，所以最终实现采用已解码图片的复用；最终版本没有逐帧 JS 绘图，也没有将 1600px 的元素布局尺寸冒充原图解码内存上限。

## 本机测量

Chrome 154、AMD 集成显卡 ANGLE/D3D11、240Hz 屏幕。桌面 1440×1000；降速检查使用 390px 宽度和 4 倍 CPU 节流，不代表真实手机。每个对照做两轮，第二轮反转版本顺序。帧间隔来自 requestAnimationFrame 采样，不等同于外部设备拍摄的屏幕呈现帧。

| 大倍率返回：首页进入照片后返回 | 旧版两轮 | 新版两轮 |
| --- | --- | --- |
| 桌面：输入至转场结束 | 1.49–3.25s | 0.699–0.707s |
| 桌面：最大帧间隔 | 1424–1733ms | 17–42ms |
| 桌面：采样帧数 | 5–6 | 107–116 |
| 4 倍 CPU：输入至转场结束 | 0.863–0.874s | 0.794–0.859s |
| 4 倍 CPU：P95 帧间隔 | 46–54ms | 33–38ms |

普通打开：桌面动画期间 P95 帧间隔为 4.3ms（旧版 4.3–8.4ms）；4 倍 CPU 时为 4.3–8.4ms（旧版 12.6–20.9ms）。

这是具体场景的测量，不是所有设备的流畅度保证。4 倍 CPU 条件下，大倍率返回仍有 75–124ms 的启动长任务；直接打开照片链接后首次返回，需要创建画廊，该场景本次约 337ms 才准备好、约 1.04s 完成。后续玻璃初始化、工具条展开仍有长帧。桌面大倍率返回的新方案主线程 CPU 时间约 98–118ms，旧版约 36–37ms：旧版在很少的帧中长时间停顿，因此不能用主线程 CPU 单项指标代替实际响应和帧间隔。

## 截图中灰字与浮雕感的原因（分析，未改阴影算法）

`toolbarInk.ts` 在背景线性亮度 0.1–0.3 之间平滑混合白字与黑字，必然经过低对比的灰区。例如背景亮度为 0.2 时，生成的灰字约 RGB 127.5，其线性亮度约 0.214，对比度仅约 1.06:1。这是公式的示例，不是对用户截图逐像素测得的数值。

临界灰色附近，阴影极性也在黑、白之间混合，因此两个方向的软阴影可能同时参与，细字会产生类似浮雕的边缘。采样取自玻璃前的照片画布，再近似叠加白色蒙层，与折射和模糊后的最终背景并不完全相同。元信息采用较小的装饰字体，进一步放大了这些问题。该问题需要先保证字形主体对比度，再评估局部反色软阴影；本轮按分析请求保留已回退的算法。
